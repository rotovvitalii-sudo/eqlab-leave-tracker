# EQLab · Облік відпусток і лікарняних

Прототип для тестового завдання IT Step Academy (Sintegrum): система обліку відпусток і лікарняних для компанії на 50 людей. Ролі: співробітник, менеджер, адміністратор.

## Джерела правди
- [docs/spec.md](docs/spec.md) — затверджена специфікація v1.0. **Єдине джерело вимог.**
- [docs/research.md](docs/research.md) — ресерч ринку. Пояснює рішення MoSCoW; вимог не задає.
- [docs/worklog.md](docs/worklog.md) — журнал часу. Оновлювати на початку й наприкінці кожного кроку, лише реальним часом з `date`.

## Принципи
1. **Строго за spec.md.** Якщо чогось там немає, ми цього не робимо. Нова ідея або суперечність → спершу питання замовнику і правка spec, потім код.
2. **Лише Must.** Should / Could / Won't не реалізуємо навіть «заодно».
3. **Простота понад гнучкість.** Ніяких абстракцій «на майбутнє», state-менеджерів і зайвих залежностей. Мінімум екранів, стандартні компоненти shadcn/ui.
4. **Правила живуть у базі.** Бізнес-правила зі spec §5 (баланс, перетини, статуси, скасування) реалізуються у функціях Postgres. UI лише показує їх і дублює підказки. Правило має працювати й при прямому зверненні до Data API.
5. **Фази й кроки зі стопом.** Після кожного кроку — короткий звіт «що зроблено / як перевірити». Далі лише після «ок» замовника.

## Стек
- Next.js (App Router, TypeScript), Tailwind CSS, shadcn/ui.
- Supabase: Postgres, Auth (email + пароль для 3 демо-акаунтів), Storage (бакет `sick-documents`).
- Клієнт `@supabase/ssr`: серверний клієнт у Server Components / Server Actions, браузерний — лише там, де без нього не обійтися.
- Хостинг: Vercel (Hobby), деплой із GitHub.

## Безпека (обов'язково)
- **На фронтенді й у репозиторії — лише publishable (anon) ключ.** Service role / secret ключ ніколи не потрапляє в код, `.env*`-файли в git і змінні `NEXT_PUBLIC_*`. Застосунку він не потрібен.
- Змінні оточення:
  - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — публічні;
  - `DEMO_PASSWORD` — лише на сервері: Server Action входу демо-кнопками; не з префіксом `NEXT_PUBLIC_`.
- `.env.local` у `.gitignore`; у репозиторії лише `.env.example` без значень.
- **RLS увімкнено на кожній таблиці, у кожної — явні політики за ролями** (spec §5.6). Таблиця без політик = помилка.
- Storage: політики на `storage.objects` для `sick-documents`. Доступ мають власник, його менеджер і адміністратор.
- Подання для колег (`colleague_absences` або подібне) віддає лише дозволені поля: ПІБ, відділ, дати, тип; лише статуси `approved` / `registered`.
- Функції `security definer`:
  - завжди з `set search_path = ''`;
  - перевіряють `auth.uid()` і роль;
  - `execute` дозволено лише `authenticated`.
- Роль користувача визначається з таблиці `employees` за `auth.uid()`, а не з клієнта.

## База даних
- Міграції — SQL-файли в `supabase/migrations/` з префіксом `YYYYMMDDHHMMSS_`. Одна міграція — одна логічна зміна.
- Seed і скидання демо-даних — одна функція `reset_demo()`. Seed = виклик цієї функції, кнопка «Скинути демо-дані» = вона ж. Дати будуються відносно `current_date`.
- Часовий пояс бізнес-логіки — `Europe/Kyiv`.
- Дні заявки (`days`) рахує база:
  - щорічна відпустка — календарні дні мінус `holidays`;
  - лікарняний і «без збереження» — усі календарні дні.

## Інтерфейс
- Мова — лише українська. Дати у форматі `дд.мм.рррр`. Тексти помилок зрозумілі людині («Недостатньо днів: доступно 6, потрібно 9»).
- Mobile-first: усі екрани працюють на ширині 375 px без горизонтального скролу. На телефоні таблиці стають картками.
- Біля підрахунку днів відпустки — примітка про воєнний стан (spec §3, виноска ¹).

## Структура (план)
```
app/                 маршрути: /login, /employee, /manager, /admin
components/          UI-компоненти, components/ui — shadcn
lib/supabase/        server.ts, proxy.ts (оновлення сесії; Next.js 16: proxy замість middleware)
lib/session.ts       поточний співробітник і роль, requireRole
supabase/migrations/ схема, RLS, функції, reset_demo
supabase/tests/      RLS-тести на PGlite
docs/                spec.md, research.md, worklog.md
```

## Команди
```bash
npm install          # залежності
npm run dev          # локально: http://localhost:3000
npm run build        # продакшн-збірка (має проходити перед кожним звітом)
npm run lint         # ESLint
npm run test:db      # міграції + RLS-тести на PGlite (без Docker)
npx supabase link    # один раз: прив'язка до проєкту (робить замовник, потрібен пароль БД)
npx supabase db push # застосувати міграції до Supabase
```

## Готовність кроку
- `npm run build` і `npm run lint` проходять без помилок.
- Критерії приймання зі spec §9, що стосуються кроку, перевірено вручну за потрібні ролі.
- Для змін у схемі перевірено RLS: від імені співробітника чужі заявки й файли недоступні.
- `docs/worklog.md` оновлено.
